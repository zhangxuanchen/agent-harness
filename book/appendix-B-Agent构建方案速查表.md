## E 层 · 执行环境

| 要构建什么 | 解决的问题 | 关键实现 | 章节 |
|-----------|-----------|---------|------|
| Docker 加固沙箱（非 root + seccomp + cap-drop + 资源限制） | Agent 执行代码的不可逆破坏风险——一条 `rm -rf` 消灭整个项目 | `SandboxConfig` + Docker 参数配置。最小可行沙箱：非 root 用户 + `--cap-drop=ALL` + seccomp + CPU 1核/内存 512MB + 30s 超时 | Ch4 §4.2 |
| 文件系统快照/回滚 | Agent 调错工具导致文件被污染后无法恢复 | OverlayFS 写时复制 —— base 层只读，diff 层可写。回滚 = 删除 diff 层，毫秒级恢复 | Ch4 KP 4.3.3 |
| 三层文件系统架构（Overlay + Composite + Projection） | 多用户共享基础文件 + 不同路径不同存储 + 容器销毁不丢工作区 | AgentScope 设计模式——OverlayFS 双层（共享下层+私有上层）、Composite 路径路由、Projection 白名单投影 | Ch4 §4.7 |
| 沙箱预热池 | Docker 冷启动 2.1s 在高频场景不可接受 | 维护 N 个热容器（poolSize = 历史并发峰值 × 1.2），请求到达直接分配，延迟降到 < 10ms | Ch4 KP 4.4.1 |
| 网络白名单代理 | Agent 可能访问不该访问的外部服务 | 容器 `--network` 限定制网络 + DNS 代理过滤，只允许白名单内的域名和端口 | Ch4 KP 4.3.2 |

## T 层 · 工具接口

| 要构建什么 | 解决的问题 | 关键实现 | 章节 |
|-----------|-----------|---------|------|
| 五要素描述框架 | 工具描述不精确 → 55% 准确率。模型在"猜"参数签名 | 名称 + 参数（类型+约束+required） + 返回值 + 错误模式 + 使用示例。准确率 55%→92% | Ch5 KP 5.6.1 |
| 结构化错误协议 | 工具返回纯文本错误 → Agent 无法程序化理解 | JSON 格式：`{errorCode, suggestion, retryable}`。自修复率 32%→78% | Ch5 KP 5.5.4 |
| Semantic Router Top-K 预选 | 50+ 工具时准确率崩塌（BFCL：95%→0-20%） | 向量相似度检索 Top-5 候选 → 模型精选 1 个。Token 节省 99% | Ch5 KP 5.4.2 |
| 幂等键机制 | 写操作（退款/扣款/删除）重复执行 | Redis SETNX + idempotencyKey。相同 key 只执行一次 | Ch5 KP 5.5.1 |
| MCP 服务器连接 | 工具来自多个外部服务，需要标准化发现和调用 | MCP Client 配置 + Tool Router 注册。自建工具走 @Tool 注解，外部工具走 MCP | Ch5 KP 5.2.2 |
| 工具版本管理与退役 | 工具升级后旧版本仍在被调用 | 版本号前缀 + 废弃通知 + 灰度切换。旧版本保留 30 天后移除 | Ch5 KP 5.7.2 |

## C 层 · 上下文与记忆

| 要构建什么 | 解决的问题 | 关键实现 | 章节 |
|-----------|-----------|---------|------|
| 三层记忆架构 | 对话长了 Agent 忘事、跨会话失忆 | 工作记忆（最近 3-5 轮原文） + 情景记忆（SQLite FTS5 全文检索） + 语义记忆（向量+KV 存储）。按需检索，零 Token 浪费 | Ch6 §6.2 |
| 上下文压缩（Compaction） | 50 轮对话后上下文溢出模型窗口 | 结构化压缩：目标 + 状态 + 关键发现 + 后续计划。保留最近 10 轮原文，早期对话压缩为摘要 | Ch6 KP 4.4.1 |
| 目标锚定（Goal Anchoring） | Agent 逐渐偏离最初目标（上下文漂移） | System prompt 中持续注入当前目标。O 层 embedding 检测漂移——cosine similarity < 0.6 触发告警 | Ch6 KP 4.4.2 |
| AGENTS.md 双层缓存 | 改了规则文件 Agent 不知道、每次读文件开销大 | 内存缓存 + 文件 mtime 检测。stat() 微秒级判断是否需要重读，读写分离 | Ch6 KP 4.5.1 |
| KV-cache 稳定前缀 | 缓存命中率决定 50%+ 的成本。不稳定前缀导致缓存全作废 | System prompt + 工具定义 = 稳定前缀（不变）。用户消息 + 工具历史 = 动态后缀。稳定前缀中严禁动态内容 | Ch6 §6.3 |
| RAG 检索管道 | Agent 需要外部知识但不知道从哪查 | Query Rewrite → Embedding → Top-K Retrieval → Cross-Encoder Rerank → Context Injection | Ch6 KP 4.5.2 |

## L 层 · 编排控制

| 要构建什么 | 解决的问题 | 关键实现 | 章节 |
|-----------|-----------|---------|------|
| 工程化 ReAct 循环 | 裸 ReAct 会死循环、成本失控 | 步数上限 + 重复检测 + 超时熔断 + 状态外置 + 错误恢复。五组件缺一不可 | Ch7 §7.1 |
| PipeReAct 混合编排 | 纯 Pipeline 不灵活、纯 ReAct 成本高 | Pipeline 骨架（确定性步骤） + ReAct 肌肉（不确定性处理） + V 层质量门（每步验证） | Ch7 KP 5.7.1 |
| Agent 状态机 | 崩溃后不知道执行到哪一步 | IDLE→RUNNING→REASONING→TOOL_CALL→COMPLETED/FAILED/PAUSED。状态持久化到外部存储，崩溃后恢复 | Ch7 §7.5 |
| 编排模式选型决策 | 不知道用 Pipeline/黑板/层级/网状哪种 | 四步递进判断：工具返回可预测性 → 步数 → 探索需求 → 安全约束 → 输出推荐模式 | Ch7 KP 5.6.2 |
| 检查点/恢复 | Agent 跑了 20 步后崩溃，从头开始太贵 | WAL 模式——先写日志再执行。增量检查点 + 全量快照交替。恢复时从最近全量回放增量 | Ch7 KP 5.5.2 |

## O 层 · 可观测性

| 要构建什么 | 解决的问题 | 关键实现 | 章节 |
|-----------|-----------|---------|------|
| 五标签成本追踪 | 月底账单看不清钱花在哪 | user_id + session_id + task_type + model_name + tool_name。按标签 GROUP BY 聚合，生成成本热力图 | Ch8 KP 4.4.1 |
| Guides vs Sensors 二分框架 | 观测只是"事后看"不够——需要在执行前就引导正确行为 | Guides（Token 预算、工具限制）→ 前置指令减少偏差。Sensors（Trace、Metrics、Logs）→ 后置感知检测偏差 | Ch8 KP 4.2.1 |
| 三级观测指标 | 开发者/SRE/产品经理看不同粒度的数据 | 调用级（P95 延迟、Token 成本）→ 任务级（端到端成功率）→ 业务级（用户满意度、FCR） | Ch8 §8.3 |
| Agent Event Log（JSONL） | 出事后无法回放 Agent 的完整推理过程 | Append-only JSONL。每条带 traceId/spandId/timestamp。支持"时间旅行"调试和问题还原 | Ch8 KP 4.5.1 |
| OpenTelemetry 全链路集成 | 分布式 Agent 系统的调用链不可见 | AgentScope + Micrometer + OTel Exporter。Trace 关联 traceId/sessionId，跨服务追踪 | Ch8 §8.1 |

## V 层 · 验证评估

| 要构建什么 | 解决的问题 | 关键实现 | 章节 |
|-----------|-----------|---------|------|
| EDD 评估驱动开发 | 改 prompt 后不知道是改好了还是改坏了 | 先写 100 个回归任务作评估集 → 每次变更自动跑全量 → 故障 > 10% 阻断部署 | Ch9 KP 5.1.2 |
| 五阶段质量控制循环 | 评估需要标准化流程，不能每次随手测 | 锚定（定义基准）→ 就绪（变更审查）→ 执行（嵌入式评判）→ 评判（LLM-as-Judge）→ 回归（自动化验证） | Ch9 §10.2 |
| LLM-as-Judge 偏差治理 | LLM 评判自己的输出有系统性偏差 | AB/BA 交换消除位置偏差 + 长度截断消除冗长偏差 + 多次投票消除分数区间偏差。Pearson r > 0.8 验证 | Ch9 §10.3 |
| 影子流量 A/B 测试 | 新版本直接全量部署风险太高 | 5% 流量走新版本（不回传用户） → 积累统计样本 → p < 0.05 显著 → 逐步扩流至 100% | Ch9 KP 5.5.1 |
| 统计显著性检验 | Agent 的非单调性使单次分数不可靠 | p < 0.05 + Cohen's d > 0.2 + N ≥ 100。满足三个条件才构成"真实改进" | Ch9 KP 5.2.4 |

## G 层 · 治理安全

| 要构建什么 | 解决的问题 | 关键实现 | 章节 |
|-----------|-----------|---------|------|
| 四检查点安全防线 | 攻击可以从输入、工具调用、输出、会话任意位置进入 | ① 输入检查（正则+分类器）→ ② 工具调用检查（白名单+参数校验）→ ③ 输出检查（PII脱敏+合规校验）→ ④ 会话异常检测 | Ch10 KP 4.2.1 |
| 三级安全管线 | 单一检测不够——正则漏高级攻击，LLM 太慢 | L1 正则（<1ms/80%检出）→ L2 分类器（<50ms/15%）→ L3 LLM（<500ms/5%）。平均延迟 < 20ms | Ch10 KP 4.2.2 |
| 声明式宪法（YAML） | 安全规则散落在代码中，不可审计 | YAML/JSON 集中管理。每条规则带 reason 字段。Git 版本控制，变更走审批 | Ch10 KP 4.3.1 |
| WORM 审计日志 | 出了安全事故无法追溯 | Append-only 日志 + Merkle Tree 完整性校验。金融/医疗合规的基础要求 | Ch10 KP 4.3.2 |
| 多租户存储隔离 | 不同用户的 Agent 数据和状态互相可见 | Linux namespace + cgroups 容器隔离。每用户独立的 state 命名空间 + OSS bucket | Ch10 KP 4.3.2 |

## 跨层构建 · 全栈模式

| 要构建什么 | 解决的问题 | 关键实现 | 章节 |
|-----------|-----------|---------|------|
| 四阶段门禁 CI/CD | 每次部署前自动验证 Agent 没有故障 | Eval Gate（100 回归任务）→ Perf Gate（P95 < 2×）→ Policy Gate（安全规则）→ Human Gate（高风险审批）。任一失败自动回滚 | Ch16 KP 4.1.1 |
| 渐进式 Canary 部署 | 全量部署风险太高 | 5%（1h）→ 20%（4h）→ 50%（24h）→ 100%。每阶段自动指标判定，失败自动回滚 | Ch16 KP 4.3.1 |
| 四层硬预算体系 | 一个用户的无限循环拖垮整个组织 | L1 节点（$0.50/步）→ L2 任务（$2/次）→ L3 用户（$10/天）→ L4 组织（$100K/月）。独立触发，下层优先 | Ch17 KP 4.3.1 |
| 燃烧率监控 | 成本异常逐渐加速，绝对值告警滞后 | burnRate = 已消耗预算% / 已消耗时间%。burnRate > 1.2 触发自动降级，> 1.5 触发熔断 | Ch17 KP 4.2.1 |
| 数据飞轮闭环 | Agent 上线后效果持续下降而非持续变好 | 48 小时闭环：O 层采集错误 → 数据清洗标注 → 模型微调/路由优化 → 部署上线 → O 层评估效果 | Ch12 KP 4.3.1 |
| 事故复盘模板 | 出事后修 bug 但同类问题反复出现 | 五步模板：时间线还原 → 根因定位到 Harness 层 → 缺陷登记 → 回归覆盖 → 加固部署 | Ch16 KP 4.4.1 |

### E 层 · 沙箱选型

| 决策问题 | 选型标准 | 方案对比 | 推荐场景 | 章节 |
|---------|---------|---------|---------|------|
| 用什么沙箱技术？ | 安全需求 → 性能需求 → 成本约束，三步定位 | 进程级（零隔离, <1ms）\| Docker（中等隔离, 2s冷启动）\| gVisor（强隔离, <1s冷启动）\| Firecracker（最强, 125ms）\| WASM（最轻, 1ms启动） | 内部工具→进程级；外部API→Docker加固；多租户→Firecracker；短脚本→WASM | Ch4 §4.2, §4.5.1 |
| 单任务隔离还是多任务复用？ | 安全性优先→单任务隔离；延迟优先→预热池复用 | 每次新建容器 = 最高安全 + 最高延迟；预热池复用 = 中等安全 + 毫秒级延迟 | 代码执行→单任务隔离；客服Agent→预热池复用 | Ch4 KP 4.4.2 |
| 什么时候上三层文件系统？ | 用户数 > 10 且需要共享基础文件 | Overlay(写时复制) + Composite(多后端) + Projection(白名单投影) | 单用户→单容器；多用户→Overlay+Projection；多用户+多存储→全三层 | Ch4 §4.7 |

### L 层 · 编排模式选型

| 决策问题 | 选型标准 | 方案对比 | 推荐场景 | 章节 |
|---------|---------|---------|---------|------|
| 用哪种编排模式？ | 任务结构化程度→耦合密度gamma | Pipeline(gamma>0.7,确定性) \| ReAct(灵活性,高成本O(N²)) \| Plan-Execute(计划可预测) \| ReWOO(最低成本O(N)) \| 层级(Leader-Worker) | 固定流程→Pipeline；探索任务→ReAct；成本敏感→ReWOO；复杂分解→层级 | Ch7 §7.3, §7.6 |

## 最小可行 Harness（MVP 配置）

如果只能先做三层，按这个顺序：

```
1.  G 层 · 输入检查 + 工具白名单    ← 防止安全事故（不可逆损失）
2.  V 层 · 100 任务回归评估集       ← 知道改好了还是改坏了
3.  E 层 · Docker 加固沙箱          ← Agent 的行动在隔离环境执行
```

这三层构成 E+V+G 生存三角——是 Ch0 所说的"线上硬性要求"。无论 Agent 的业务逻辑多简单，没有这三层 = 拿生产数据赌博。
