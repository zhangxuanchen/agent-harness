# Harness 本质论：概率预算购买确定性

> 用途：第 6 章（或全书总论）的写作素材，可作为"为什么 harness 值得做"的章节题眼或总结论点。

***

## 核心论点

> LLM 是不可控的概率引擎，harness 的工作是把它装进可控的壳：能确定的变成协议，确定不了的用预算管理，管理的前提是度量——预测失败，然后花钱买确定性。

***

## 一、harness 的设计起点是"枚举死法"，不是"写功能"

这章学过的每一个机制，没有一个是正向设计出来的，全都是**先枚举一种死法，再写解药**：

| 预测到的失败事件           | 对应的机制                 |
| ------------------ | --------------------- |
| 目标被新内容挤到中间区烂掉      | Goal-pin 每轮重注入        |
| 压缩摘要堆叠成 A→B→C 矛盾版本 | Head-anchoring 合并成唯一  |
| 关键事实被压缩模型改写模糊      | Fact-pin 锁死 verbatim  |
| 压缩中途崩溃留下孤儿锁        | 状态机 + OrphanLock 恢复判定 |
| 日志被事后篡改            | invariant 重算 + 严格相等比对 |
| 早期事实被遗忘            | 三层分区 + 索引钩子           |
| 记忆衰减、话题漂移          | 双权重排序 + 漂移检测          |

所以 harness 工程是**错误模型驱动设计**（EDD）——设计者的核心工作不是"写功能"，是"枚举这个 Agent 会怎么死，然后逐个降低死法发生的概率"。

***

## 二、三区光谱：从概率到确定性

同一个引擎里的机制，按"对结果的控制力"可以排成一条光谱：

<br />

```
概率区 ←————————————→ 控制区 ←————————————→ 确定区
（内容层）              （策略层）              （协议层）

模型生成            五区预算             压缩状态机
LLM 推理输出         三层分区             CAS 乐观锁
摘要融合             压缩阈值             invariant 重算
检索排序             预算监控             纯函数渲染
                                           append-only 日志

不可控              可调参               可保证
赌概率              规则推方向            不参与概率游戏
```

**关键洞察：工程方向永远是从左往右搬。** 内容层压不下来（模型生成本质），就框住它；策略层是"调参"——用规则把概率往期望方向推；协议层是"保证"——根本不参与概率游戏。

***

## 三、确定性不是免费的——它是用概率预算买的

每个确定性都是明码标价的：

| 买的确定性                   | 付的账单                             |
| ----------------------- | -------------------------------- |
| 目标不遗忘（goal\_round 每轮重申） | 每轮 30-50 tokens，50 轮累计 1.5K-2.5K |
| 还原命中率 30% → 80%+        | 索引钩子 +100\~200 tokens            |
| checkpoint 合并成唯一        | 压缩时 KV-cache 失效一次                |
| 记忆保鲜（双权重排序）             | 15% 预算 + 排序计算开销                  |
| 篡改可检测                   | 事件溯源存储 + 重算计算开销                  |
| 压缩不崩溃                   | 状态机 6 态 + OrphanLock 恢复逻辑        |

所以五区预算本质上不是"空间管理"，是**确定性经济的账本**——每个机制都在花 token 买保证。harness 做的是一笔持续的**确定性套利**：花廉价的东西（token、复杂度、一次缓存重建），换昂贵的东西（不再崩溃、不再遗忘、不可篡改）。

***

## 四、第三根支柱：度量

"预测事件"的前提是知道现状。没有度量，连"当前概率是多少"都不知道，控制就是盲调。

| 度量手段             | 喂给谁  | 触发什么           |
| ---------------- | ---- | -------------- |
| 探针测早期事实召回率       | 腐烂检测 | 三种 pin 锚定      |
| 工具历史占比 52% > 45% | 预算监控 | 压缩状态机启动        |
| 组装审计日志           | 故障归因 | 组装遗漏/排列错位/压缩丢失 |
| 漂移检测 cosine      | 漂移告警 | 强制回溯           |
| invariant 重算比对   | 篡改检测 | 判定日志被篡改        |

***

## 五、完整闭环

```
枚举死法（错误模型）→ 度量现状（探针/审计）→ 花预算买确定性（机制）
        ↑__________________结果反馈__________________↓
```

三段缺一不可：

- **没有枚举**：不知道有哪些死法，机制无处落地
- **没有度量**：不知道现状，控制是盲调
- **没有预算**：确定性买不起，token 先爆

## 附：三种 pin 的唯一性辨析（写作时易混点）

| pin            | 唯一性形态                                | 机制目的  |
| -------------- | ------------------------------------ | ----- |
| Head-anchoring | **版本唯一**（合并折叠，只有最新状态）                | 防堆叠矛盾 |
| Fact-pin       | **容器唯一、内容清单**（一个块，多条事实不折叠）           | 防改写模糊 |
| Goal-pin       | **对象唯一、文本多条**（一个持久 Goal 对象，每轮一条注入文本） | 防位置遗忘 |

口诀：**位置 = 失效发生地**——目标死在"被挤掉"就在尾部补位；进度死在"堆叠矛盾"就在头部合并；事实死在"被改写"就在压缩区锁死。
