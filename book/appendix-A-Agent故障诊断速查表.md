## 工具相关（T 层）

| 症状 | 根因 | 修复手段 | 章节 |
|------|------|---------|------|
| Agent 调用了不存在的工具或传入不存在的参数 | 工具描述不够精确，模型在"猜"参数签名 | 五要素描述框架优化工具描述：名称、参数（含类型和约束）、返回值、错误模式、使用示例。工具调用前做参数 Schema 校验 | Ch3 KP 3.1.2 五种故障模式<br>Ch5 KP 5.1.1 四元组与五要素框架 |
| Agent 在 50+ 个工具时频繁选错工具 | 工具数量超出模型选择能力，49→741 工具准确率从 95% 降到 0-20% | Semantic Router Top-K 预选（向量相似度检索 Top-5 候选→模型精选 1 个），Token 节省 99% | Ch5 KP 5.4.3 工具怎么选 |
| 工具调用返回后 Agent 无法正确处理错误 | 错误信息是纯文本，Agent 无法程序化理解 | 结构化错误返回协议（JSON 格式含 errorCode/suggestion/retryable），恢复成功率 32%→78% | Ch5 KP 5.5.3 超时重试与错误恢复 |
| 同一个工具操作重复执行了两次（如重复扣款） | 缺少幂等性保障 | 幂等键 + 去重存储（Redis SETNX），写操作须带 idempotencyKey | Ch5 KP 5.5.1 幂等性 |
| 换了新框架后工具全部要重写 | 工具描述与框架耦合 | 五要素描述格式是框架无关的，工具描述与框架解耦即可跨框架迁移 | Ch5 KP 5.6.2 工具版本管理与退役 |
| 不确定该用 Function Calling、MCP 还是 A2A | 协议选型缺决策框架 | 决策树：单 Agent + <5 工具→Function Calling；多服务→MCP；多 Agent→A2A | Ch5 §5.3 |

## 上下文与记忆（C 层）

| 症状 | 根因 | 修复手段 | 章节 |
|------|------|---------|------|
| Agent 在第 10 步之后开始忽略最初获取的关键信息（如文件路径、端口号） | 上下文腐烂（Decay）：早期信息被中间大量工具输出和推理过程稀释 | 每 5 步注入诊断 probe 检测腐烂，阳性→触发上下文压缩 + 注入关键信息锚点 | Ch6 KP 6.3.1 上下文腐烂与漂移 |
| Agent 逐渐偏离最初目标，开始做无关的事（如本来要分析销售数据，第 8 步变成写博客） | 上下文漂移（Drift）：目标被中间上下文"替换"，Agent 没有独立的目标存储 | 目标强制回归：system prompt 持续注入当前目标 + O 层 embedding 检测漂移（cosine similarity < 0.6 触发告警） | Ch6 KP 6.3.1 上下文腐烂与漂移 |
| Agent 对上下文中间位置的信息反应迟钝 | "Lost in the Middle" 注意力衰减：中部位置准确率比首尾低 20+ pp | 关键约束放首部或尾部，避免放在上下文中间。每轮 LLM 调用前检查关键信息的位置 | Ch6 KP 6.1.1 注意力衰减三机制 |
| 对话长了之后 cost 暴涨 | 上下文 O(N²) 膨胀——每一步都把前面所有内容重新喂给模型 | KV-cache 稳定前缀设计（系统提示+工具定义不动），动态后缀（用户消息+工具历史）。开启 Prompt Caching | Ch6 KP 6.1.3 KV-cache 前缀复用<br>Ch6 KP 6.1.2 上下文成本结构 |
| Agent 在多个会话间无法记住用户偏好 | 缺少跨会话持久记忆 | 三层记忆架构：工作记忆（最近 3-5 轮）、情景记忆（FTS5 全文检索）、语义记忆（向量+KV 存储） | Ch6 §6.2 工作记忆（三层记忆架构） |
| 上下文窗口经常溢出 | 没有上下文预算管理 | 五区域预算分配（system/tools/history/retrieval/headroom）+ ContextBudgetMiddleware 自动管理 | Ch6 KP 6.1.2 上下文成本结构与预算控制 |

## 编排与循环（L 层）

| 症状 | 根因 | 修复手段 | 章节 |
|------|------|---------|------|
| Agent 反复执行同样的工具调用，不推进任务（如反复查同一个空结果） | 循环卡死：缺少去重和终止条件 | 步数硬限制 + 最近 3 步去重检测（连续重复→强制终止或切换策略） | Ch3 KP 3.1.2 五种故障模式<br>Ch7 KP 7.1.1 ReAct 工程实现 |
| Agent 执行到一半突然报错退出，无法恢复 | 缺少检查点（checkpoint）机制 | 状态外置：每步后持久化 AgentState 到 Redis/DB，失败后从最近 checkpoint 恢复 | Ch7 §7.7 状态机与检查点 |
| 不确定该选哪种编排模式（ReAct/Pipeline/层级/网状） | 缺少编排模式选型框架 | 四步判断：工具返回可预测性→步数→探索需求→安全约束。默认选层级模式（最稳健） | Ch7 KP 7.4.1 编排模式基准与决策树 |
| Pipeline 模式每步错误导致整个流程失败 | 缺少步间隔离和局部重试 | 每步独立 V 层质量门 + 局部重试（最多 3 次）+ 全局超时 | Ch7 KP 7.6.2 管道端到端成功率优化 |
| Agent 步数爆炸，一个简单任务跑了 80 步 | 没有步数上限和进展监控 | 步数硬上限（默认 30）+ 进展分数监控（连续 5 步无进展→终止）+ 超时熔断 | Ch7 KP 7.1.2 循环收敛性保证 |
| 多 Agent 协作时任务分出去了没人认领 | 任务分配缺少确认机制 | Leader-路由通信 + 任务心跳 + 超时回收 | Ch15 KP 15.6.1 级联故障五道防线 |

## 安全与治理（G 层）

| 症状 | 根因 | 修复手段 | 章节 |
|------|------|---------|------|
| 用户输入"忽略之前的指令"后 Agent 行为异常 | 提示注入攻击：缺少输入过滤 | L1 正则过滤（<1ms）+ L2 分类器检测（<50ms）+ L3 LLM 审查（<500ms）三级安全管线 | Ch10 §10.2 四检查点 |
| Agent 输出了用户的数据库密码或其他敏感信息 | 输出缺少 PII 脱敏 | 输出审查：正则匹配 PII 模式→掩码替换（如 `***`）。SafeGuardMiddleware 配置输出检查规则 | Ch10 KP 10.2.1 检查点威胁类型与防护手段 |
| Agent 调用了不该调用的工具（如 DROP TABLE） | 工具白名单缺失 | 工具白名单 + 运行时权限检查（ToolPolicyMiddleware）。危险操作必须人工审批 | Ch10 KP 10.2.1 检查点威胁类型与防护手段 |
| 不确定某个 Agent 错误该谁负责 | 缺少审计和归属追踪 | WORM 存储审计日志 + 决策链追溯（每一步记录了谁/什么上下文/什么工具/什么结果） | Ch10 KP 10.3.2 审计日志 |
| 不同环境的 Agent 安全策略不一致 | 安全策略散落在代码中 | YAML 声明式宪法：集中管理策略文件，Git 版控，变更走审批。每条规则带 reason 字段 | Ch10 KP 10.3.1 声明式规则 |

## 成本（O 层 + 模型层）

| 症状 | 根因 | 修复手段 | 章节 |
|------|------|---------|------|
| 月底账单比预期高了 5 倍，不知道钱花在哪了 | 缺少成本归因和实时监控 | 五标签成本追踪（用户/任务/步骤/工具/模型）+ P99 异常检测 + 实时告警 | Ch8 KP 8.4.1 Token 成本实时归因<br>Ch12 KP 12.3.1 三层模型路由 |
| 简单查询和复杂推理用了同一个昂贵模型 | 没有模型路由分层 | 三层路由：L1 规则（简单→Haiku/Flash）→L2 分类器（编码→Sonnet）→L3 级联（复杂→Opus） | Ch12 KP 12.3.1 三层模型路由 |
| Agent 某天突然开始疯狂调用工具，费用暴涨 | 燃烧率异常：burnRate > 1.2 | 四层硬预算体系（组织级→用户级→任务级→节点级），每层独立熔断。燃烧率 > 1.2 降级，> 1.5 熔断 | Ch17 §17.3 四层预算<br>Ch17 §17.2 燃烧率 |
| 换了新模型后成本翻倍但没发现 | 模型切换缺少成本对比 | 模型路由配置中嵌入 cost-per-task 预估，切换后自动对比 P95 成本 | Ch12 KP 12.1.1 模型选择三角 |

## 质量与评估（V 层）

| 症状 | 根因 | 修复手段 | 章节 |
|------|------|---------|------|
| 新版本部署后 Agent 表现变差，但没人发现 | 缺少自动化回归评估 | EDD 评估驱动开发：每次变更自动跑 100 个回归任务，故障 > 10% 阻断部署 | Ch9 KP 9.1.2 EDD 四阶段<br>Ch16 KP 16.1.1 四阶段门禁 |
| 同一个任务跑两次评分差异很大 | Agent 的非单调性：LLM 输出的概率性导致 run-to-run 波动 5-10% | 统计检验替代单次评分：N≥100, p<0.05, Cohen's d>0.2 才判定"真实改进" | Ch9 KP 9.5.2 A/B 统计陷阱<br>Ch9 KP 9.1.1 评估四重困难（非单调性） |
| LLM 打分总是偏向长回答或排在前面那个 | LLM-as-Judge 偏差：位置偏差 + 冗长偏差 | AB/BA 交换防位置偏差 + 长度截断防冗长偏差 + 多次投票防随机波动 | Ch9 KP 9.3.1 LLM-as-Judge 偏差与治理 |
| SWE-bench 跑分很高但真实场景很差 | 基准污染：模型可能训练时见过测试数据 | 自建内部回归集（100 个典型任务），不与公开基准共享数据 | Ch9 KP 9.3.2 度量陷阱<br>Ch9 KP 9.4.2 自建评估集五步法 |

## 执行环境（E 层）

| 症状 | 根因 | 修复手段 | 章节 |
|------|------|---------|------|
| Agent 的工具执行破坏了宿主机文件 | 缺少沙箱隔离 | Docker 沙箱 + OverlayFS 快照 + 网络白名单。每次任务从干净快照启动，结束时丢弃变更 | Ch4 §4.2 五维隔离标准 |
| 同一任务跑两次结果不同，无法复现 Bug | 环境状态被上一次运行污染 | 沙箱快照/回滚：任务开始时从快照恢复，结束时丢弃所有变更。实现确定性执行 | Ch4 KP 4.1.2 状态漂移与不可变环境 |
| 高并发时沙箱冷启动 3-5 秒，用户等不了 | Docker 冷启动延迟 | 预热池：维持 3-5 个热沙箱，请求到达时直接分配。Firecracker microVM 冷启动 125ms | Ch4 KP 4.5.1 预热池策略 |
| Agent 执行了一个死循环脚本，CPU 打满 | 缺少资源配额限制 | CPU 1 核 + 内存 512MB + 磁盘 1GB + 超时 30s。超时后强制终止并回收沙箱 | Ch4 KP 4.4.1 资源配额 |
| 不确定该用 Docker 还是 gVisor 还是 Firecracker | 沙箱选型缺决策框架 | 决策树：安全需求→性能需求→成本预算。Docker 覆盖 80% 场景，高安全场景用 Firecracker | Ch4 §4.3 沙箱方案选择（四问决策法） |

## 多 Agent 协作

| 症状 | 根因 | 修复手段 | 章节 |
|------|------|---------|------|
